# Counterexample-Guided Correlation Algorithm for Translation Validation

**Author:**
- Shubhani Gupta, Abhishek Rose, Sorav Bansal (Indian Institute of Technology Delhi)<br/>

**Source:** OOPSLA 2020 (Proc. ACM Program. Lang. 4, Article 221)

**Link:** https://doi.org/10.1145/3428289<br/>

**Demo:** online equivalence checker at http://compiler.ai/

## Key insight

With the invariant inference algorithm fixed, translation validation reduces to finding the product CFG that correlates the two programs' transitions, and the counterexamples that invariant inference already produces for free are enough to prune and rank candidate correlations. Counter searches this exponential space best-first with a backtracking search, correlates whole pathsets so one product-CFG edge can stand for an exponentially large set of program paths, and needs neither execution traces nor a guessed alignment predicate.

## Basic idea

Translation validation checks that optimized x86 assembly refines the unoptimized LLVM IR it was compiled from, and a bisimulation proof [2] amounts to a product CFG (edges correlate transition paths of the two programs) plus inductive invariants at its nodes [1]. For a small example pair at unroll bound 8 there are about 10^14 candidate product CFGs, so Counter restricts the space using four observations about real compilations [3] and explores it with a best-first backtracking search [4]. The search is guided by counterexamples: the invariant inference engine maintains, at each product-CFG node, a candidate invariant (the strongest cover of a predicate grammar over the known counterexamples) and a set of SMT-generated counterexamples, and Counter propagates those counterexamples forward to discard candidate correlations they contradict and to rank the remaining ones by how many live variables the recomputed invariant relates. Correlations pair full pathsets, sets of mutually exclusive paths between fixed endpoints, at a bounded unroll factor [5], so one edge absorbs a vector loop body's worth of unrolled source paths, and each candidate must satisfy a one-way criterion checked with SMT: whenever the assembly traverses its pathset, the source must traverse one of the paths in its partner. A proof means a bisimulation was found, failures are inconclusive, and transformations that do not preserve program structure (loop fusion, tiling, interchange, rerolling) are out of scope [8]. Counter proves all but four of the 84 TSVC program pairs used by prior work and all 54 loop-nest pairs taken from the LORE repository, expands up to 515 times fewer candidate paths on average than a static depth-first variant of the search (which ran out of time or memory on 39 of the 219 pairs), and found three bugs in diet libc.

## Illustrative example: incremental unrolling

**The pair.** Target T is the unoptimized source (LLVM IR); rewrite R is its compiled form (-O3 assembly), unrolled by 2, which the compiler can do because the element count is even.

```text
target T                          rewrite R
T1: if p == e goto TE             R1: if p' == e' goto RE
T2: *p += 1                       R2: *p' += 1
T3: p += 4                        R3: *(p' + 4) += 1
T4: goto T1                       R4: p' += 8
                                  R5: goto R1
```

The elements are 4-byte words, so T's pointer moves one element per iteration and R's moves two, and both loops have the same starting and ending pointers.

**The correlated PC pair.** The product CFG's nodes are pairs of program points [1], and Counter considers (T1, R1), the two loop heads. Both are anchor nodes [3]: T1 is a basic-block head on the source side and R1 a loop head on the assembly side, so the anchor restriction keeps them and discards most other pairings in advance. With an even element count the loops run in lockstep, the rewrite consuming two elements per iteration and the target one, and the exit pair (TE, RE) closes the decomposition. Whether the pairing is right is not assumed; the checks below either certify it or reject it.

**The product CFG.** Two edges carry the proof (the entry edge from the start pair to (T1,R1) just pairs the initial states). The loop edge `(T1,R1) -> (T1,R1)` correlates one rewrite body `(R1-R2-R3-R4-R5-R1)` with the pathset of two target iterations `(T1-T2-T3-T4-T1)^2`, under the path condition `p + 8 <= e`. The exit edge `(T1,R1) -> (TE,RE)` correlates `(R1-RE)` with `(T1-TE)` under the condition `p == e`. The loop edge's target pathset is the right one among many: R's body consumes two elements, so exactly two target iterations happen while it runs, and the edge stays in lockstep with the invariant `p == p'` plus heap equality (both have processed the same prefix).

**Why other pairings fail, and why the chosen one passes.** A candidate that pairs one rewrite body with a single target iteration cannot work: the rewrite body advances the pointer by two elements and one target iteration by one, so the node invariant `p == p'` cannot be preserved [6], and a failing check of this kind yields an SMT model, a concrete counterexample that the search records for pruning and ranking [4]. The chosen edge passes the same checks: the one-way criterion holds (a rewrite body implies two target iterations, which the edge's target pathset contains), the invariant is preserved along the edge, and mismatched combinations are contradictory through the invariant, since R exits only when `p == e = e'`, which with `p == p'` forces T to exit too. The exit edge proves the heaps equal at (TE,RE), the node invariants form the bisimulation [2] that relates the two loops' states, the product CFG is complete, and the tool reports equivalence for the assumed even-length inputs.

**Ranking among survivors.** When several candidates survive the path-condition check, as in the paper's kernel with branches inside the loop, the propagated counterexamples decide: for each candidate the tool recomputes the strongest invariant cover of the node's counterexamples and prefers the candidate whose cover leaves the fewest live bitvector variables unrelated by affine relations, first in the assembly and then in the source [4]. The paper's walkthrough shows the correct correlation ranked first because its invariant cover relates all four 32-bit subwords of a vector register to the scalar accumulator, while wrong correlations relate only two.

## Concepts and terms

**[1] Translation validation, product CFGs, and the contract.** Translation validation checks the result of each compilation instead of verifying the compiler once. The source is unoptimized LLVM IR (from C), the compiled program is x86 assembly with -O3 -msse4.2, and interprocedural optimizations are disabled so that calls to undefined functions are observable events. Equivalence is weak trace equivalence: for every input, either both programs produce identical observable event sequences (return value, heap state at exit, calls to undefined functions), or the source triggers undefined behavior, which is modeled as an error state. A proof is a bisimulation relation, represented as a product CFG: a control-flow graph for the two programs at once, whose nodes are pairs of program points, one per program (correlated PC pairs), and whose edges join pairs that the two programs can move between, each edge labeled with the transition path each program takes at that step. A path through the product CFG from the start pair to the exit pair stands for one pair of lockstep executions, and the CFG is complete when it covers every pair of behaviors the two programs can exhibit. The proof is completed by invariants at the nodes: relations between the two machine states that hold at the start, are preserved along every edge, and at the exit imply that the observables agree.

**[2] Bisimulation and bisimilarity.** A bisimulation is a relation between the states of two programs such that related states agree on what is observable and every step of either program is matched by a step of the other while keeping the relation: if the source moves from s to s' and (s, t) is in the relation, then the target moves from t to t' with (s', t') related, and symmetrically. Bisimilarity is the union of all bisimulations, so the programs are bisimilar when some bisimulation relates their initial states; bisimilar programs produce identical observable behaviors, and neither can reach a state the other cannot mimic. The one-way version, where only one program must match the other, is a simulation, which is weaker and suits refinement; Counter needs the two-way relation, and its product CFG with invariants is a bisimulation in syntactic form, with the correlated PC pairs as the related states and the edges discharging the matching obligations.

**[3] The four observations that bound the search.** (A) For most programs and transformations a product CFG exists whose invariants only need equality, inequality, and affine relations between bitvector and array values; with the invariant engine fixed, the whole problem is which product CFG to use. (B) Correlated path lengths can be bounded by a parameter L, which is set to twice the compiler's unroll factor (8 for GCC and ICC, 16 for LLVM); the factor of two covers the cool-down loops of vectorized code, where a path from a vector loop head to the exit mixes full vector iterations with up to three scalar residual iterations. (C) The candidate points are restricted to anchor nodes: on the assembly side, loop heads, the start and exit, and call-adjacent nodes suffice; on the source side, all basic-block heads and tails plus call-adjacent nodes. (D) A pathset in the assembly may be correlated with only one pathset in the source, the one that covers everything the assembly could imply, a one-way specialization. Observation D fails for despecializing transformations (for example fusing two nearly identical loops into one), which Counter therefore cannot verify.

**[4] Searching with counterexamples.** The algorithm keeps a frontier of partial product CFGs, each with inferred invariants and remembered counterexamples, and repeatedly expands the most promising one. Expanding means: pick the next uncorrelated assembly pathset (a single step, restricted to the next anchor nodes and taken in reverse post-order), enumerate candidate source pathsets as (L, m)-unrolled full pathsets from the current anchor node to every anchor node (including the empty path), and instantiate a child for each candidate whose actions match (a function call must match a function call). Each child then gets fresh counterexamples (propagated forward from the parent, where missing variable values are generated randomly, propagation stops at the third visit of a node, and a counterexample that triggers undefined behavior stops), invariant inference from scratch on the new edge, and the pruning checks: candidates whose path conditions a counterexample violates, and candidates whose recomputed invariant cover fails to relate the heaps, are dropped. Surviving children are ranked by the number of live bitvector variables not related by affine equalities (fewest first, counting the assembly then the source), with static tie-breakers preferring a smaller unroll factor and then a longer shortest path. A complete product CFG whose invariants prove observable equivalence is the proof.

**[5] Pathsets and unrolled full pathsets.** A pathset is a set of execution paths that start and end at the same node and are pairwise mutually exclusive (no path is a prefix of another). An (L, m)-unrolled full pathset from u to v contains all paths in which v occurs exactly m times and no other node more than L times; the paper's pathset notation uses series-parallel digraphs (`+` for parallel, concatenation for serial, epsilon for the empty path), which lets the path condition of an exponentially large pathset be written as a linear-sized SMT formula. Correlating a pathset with a pathset, instead of enumerating individual paths, is what makes unrolled and vectorized loops tractable: the paper's motivating case pairs `(C1-C3-C1)+(C1-C5-C1)+(C1-C7-C1)` repeated four times (81 paths, or 6561 at unroll factor 8) with the single vector body edge of the assembly.

**[6] Invariant inference and proof obligations.** A forward dataflow analysis computes at every product-CFG node a pair (INV, Gamma): a candidate invariant and a set of counterexamples. The transfer function along an edge propagates both, computes the strongest invariant cover of the data (a conjunction of predicates from a grammar: affine equalities, bitvector relations, and heap equalities `HC = HA` up to an exception set), and repeatedly adds counterexamples from failed proof obligations until the obligation holds. Each obligation is a relational Hoare triple `{INV} P ; Q {INV'}` lowered to `INV implies WP_P;Q(INV')`, where P and Q are the two correlated paths; queries use quantifier-free bitvectors, arrays, and uninterpreted functions and go to Z3, Yices2, and CVC4 in parallel. For SAT queries the tool waits past the first answer to collect counterexamples from several solvers, because solver behavior matters: Yices2 answers around 98% of queries first but tends to return monotone counterexamples (for example successive halvings) that require many refinement rounds, while the slower solvers return more diverse models.

**[7] Implementation details.** The CFGs come from symbolic executors for LLVM IR and x86 that encode edge guards and transfer functions as SMT expressions; a static analysis identifies stack slots at constant offsets from the frame pointer, a flow-sensitive intra-procedural points-to analysis classifies every memory access as stack, or not stack (globals or allocated heap), available-expression and must-reach analyses feed the invariant inference. Queries are decomposed as in the authors' prior work to avoid solver timeouts. The setup uses a five-hour limit per function, five minutes per query, and 12 GB of memory; an SMT bug found during the experiments was reported to the Yices developers and fixed.

**[8] Scope and soundness.** Counter proves bisimilarity, so its verdicts are sound when it succeeds: the product CFG with its invariants is a bisimulation witness. Failure is inconclusive. Non-bisimilar transformations are out of scope: loop tiling and interchange reorder an unbounded number of memory accesses, and rerolling needs paths of the assembly (not the source) to be unrolled. Because the restriction of Observation D can also reject some genuinely equivalent despecializing transformations, the tool can report false failures there. Counter's name records its two devices: it uses counterexamples to identify the most promising correlation, and it counts the related variables across the two programs to rank candidates.

**[9] Evaluation.** On the 28 TSVC functions that prior work also used, across three compilers (84 program pairs), Counter proves all but four; the failures (s176 with GCC, s1112 and s243 with ICC) involve tiling or interchange, and s351 with ICC involves rerolling. Three of these had been reported as successes in the prior alignment-based work because it used older compilers that did not apply those transformations. On the remaining TSVC functions whose compiled code involves vectorization, Counter proves 21 of 28 pairs for GCC, 26 of 30 for LLVM, and 38 of 60 for ICC; most failures are non-bisimilar transformations and four are invariant-inference timeouts. On 16 LORE loop-nest patterns (two variations each, two unroll factors each, 54 program pairs, with up to three loops and maximum nesting depth three) it proves everything. A static depth-first variant of the search expands up to 515 times more paths on average and abandons 39 of the 219 pairs that the best-first search proves. Comparing OpenBSD's libc against diet libc, Counter found three serious bugs, all missing type casts (for example a sign-extended character comparison in memccpy that reads past the array element), and the diet libc developers fixed them upon report.
