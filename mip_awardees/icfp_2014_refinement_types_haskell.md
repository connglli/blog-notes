## Key insight

A lazy binding need not ever produce a value, so its refinement cannot automatically be assumed as a logical fact. Sound checking must distinguish terminating bindings from computations that may diverge.

## Basic idea

Refinement types [1] attach logical predicates to ordinary types, and SMT-based checking [2] proves the implications generated by subtyping. Under lazy evaluation [3], a divergent expression can remain unevaluated while unrelated code executes, making the usual eager translation of every binding into a logical assumption unsound. The paper stratifies [4] bindings by termination behavior and uses refinements to verify decreasing recursive calls. Only justified value information enters the solver context, retaining useful reasoning without requiring every Haskell computation to terminate.

## Illustrative example

**False assumption.** Define an endlessly recursive integer expression `never`. Give it a partial-correctness refinement saying that, if it returns, its result satisfies false. Such a refinement imposes no condition on a computation that never returns.

Now consider a lazy expression that binds `unused = never` and then computes `head []`. Since `unused` is not demanded, the list access is still reached and fails.

**Unsound translation.** A checker that inserts the refinement of every binding into its logical environment obtains false from `unused`. From false it can prove any implication, including the fabricated claim that the empty list has positive length. The solver is reasoning correctly from a bad translation of program facts.

**Stratification.** Mark `unused` as potentially divergent and do not use its impossible refinement as an available value fact. The remaining context cannot prove that `[]` is nonempty, so the unsafe access is rejected.

**Recover useful information.** Replace the unused loop with a recursive list-length function. Its recursive call consumes a proper tail, whose nonnegative length is smaller than that of the matched nonempty list. A termination argument permits the checker to use the function's result refinement, for example that it agrees with the list's logical length.

For a three-element list, the size measure decreases 3, 2, 1, 0. A check that this returned length is positive can then justify an operation requiring a nonempty list. Proving the helper's termination supplies information that merely ignoring every lazy binding would lose.

## Concepts and terms

**[1] Refinement type.** A base type restricted by a logical predicate. Under partial correctness, a potentially divergent expression satisfies the predicate whenever it actually returns a value.

**[2] SMT-based checking.** Translating suitable refinement implications into formulas handled by a satisfiability-modulo-theories solver. Soundness depends on the validity of the translation as well as the solver.

**[3] Lazy evaluation.** Evaluation driven by demand. An unused binding can remain unevaluated, so reaching later code does not establish that the binding has produced a value.

**[4] Stratification.** Separating terminating computations from potentially divergent ones and controlling which refinements may be assumed. Termination checking uses well-founded decreasing measures, with refinements proving the required decreases.
