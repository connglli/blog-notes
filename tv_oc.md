## Key insight

A reordering loop transformation needs no state correspondence between source and target: writing the loop as `for i in I by ≺_I do B(i)` and its result as `for j in J by ≺_J do B(F(j))` with F a bijection, the transformation is correct as soon as every pair of iterations whose relative order F reverses computes the same result in either order, a self-contained commutation check that generalizes the classical dependence-preservation criterion and accepts some transformations dependence analysis rejects. When aliasing prevents the compile-time decision, a run-time test detects the impending violation and the computation escapes to unoptimized code instead of failing.

## Basic idea

Translation validation checks each compiler run rather than the compiler itself, requiring the target to terminate exactly when the source does and to agree with it on observable results [1]; VOC-64, the validator used here, separates optimizations that preserve the program's loop structure, which are validated by abstraction and simulation, from structure-modifying ones [2]. The structure-modifying optimizations handled are reordering transformations (interchange, reversal, fusion, distribution, skewing, tiling): each is written in the canonical form `for i in I by ≺_I do B(i)` changed to `for j in J by ≺_J do B(F(j))`, where the iteration spaces I and J are described by linear inequalities, their orders are total and usually lexicographic, and F is a bijection from J onto I [4]. Rule PERMUTE validates the transformation when every pair of iterations whose relative order F reverses satisfies B(i1);B(i2) ~ B(i2);B(i1), that is, the two bodies compute the same thing in either order; soundness is proved by induction, bubbling each displaced iteration into place [5]. The commutation premise reduces to equivalence of loop-free body fragments, which is where the structure-preserving machinery returns: rule VALIDATE maps target cut-points to source cut-points, relates source variables to guarded target expressions, and generates one verification condition per simple target path for CVC to discharge [3]. A dependence-based variant of the rule is stricter, requiring every conflicting pair of accesses (flow, anti-, or output dependence) to keep its source order; CVC checks show it implies PERMUTE for simple bodies, and it is the form used for run-time validation [6], where a test that must fire before the violation occurs (the testability property) triggers an escape to the original loop order or to a smaller tile [7]. The framework is implemented in VOC-64 and was exercised on the optimization pipeline of the SGI Pro-64 compiler [8].

## Illustrative example: interchanging a shifted-window loop

**The transformation.** A compiler interchanges the loops of
```
for i = 1..N:
  for j = 1..M:
    c[i,j] = c[i-1, j+d] + 1
```
where d is a loop-invariant integer, so that j becomes the outer index:
```
for j = 1..M:
  for i = 1..N:
    c[i,j] = c[i-1, j+d] + 1
```
In the canonical form [4], the iteration space I = {(i,j) : 1 ≤ i ≤ N, 1 ≤ j ≤ M} is ordered lexicographically with i most significant (order ≺_I), J is the same set ordered with j most significant (order ≺_J), F(j,i) = (i,j), and F⁻¹(i,j) = (j,i). F is a bijection, so only the commutation premise of rule PERMUTE [5] needs checking.

**The commutation check.** Source order ≺_I goes row by row, target order ≺_J column by column, so a pair of iterations is reversed exactly when the source-first iteration has the larger column: (i1,j1) ≺_I (i2,j2) with i1 < i2 and j1 > j2. Iteration (i,j) writes c[i,j] and reads c[i-1, j+d]. For a reversed pair the only possible interference is that iteration (i2,j2) reads the cell iteration (i1,j1) writes, which happens when i2 = i1+1 and j2 = j1-d, and since j1 > j2 this requires d > 0; the other direction would need i2 = i1-1 and is impossible as i1 < i2. So when d ≤ 0 no reversed pair interferes, the two bodies commute, and the premise holds. When d > 0 (and the bounds put such pairs in range), the reversed pair with i2 = i1+1, j2 = j1-d reads a cell before the target order writes it, so the premise fails. The dependence-based variant [6] gives the same answer: the only dependence runs from the write in (i,j) to the read in (i+1, j-d), and the transformed order keeps it, (j,i) ≺_J (j-d, i+1), exactly when d ≤ 0. In the paper's CVC runs the analogous check accepts the body reading a[i-1,j-1] (d = -1) and rejects the body reading a[i-1,j+1] (d = 1). In general, commuting two loop bodies is precisely the kind of condition rule VALIDATE [3] discharges with CVC; here it is settled by the direct argument about the two accesses.

**A run-time instance.** Let the window offset be computed at run time as d = j - 7, so d ≤ 0 can no longer be shown for every column. The paper's general interchange test [7] applied to an iteration (i,j) whose read index is (i-1, j+d) gives (r1 < i1) ∧ (r2 > i2) with (r1, r2) = (i-1, j+d) and (i1, i2) = (i,j), that is, (i-1 < i) ∧ (j+d > j), which reduces to d > 0; d depends only on j, so the test is hoisted out of the inner loop:
```
for j = 1..M:
  d = j - 7
  if (d > 0) goto escape
  for i = 1..N:
    c[i,j] = c[i-1, j+d] + 1
escape:
  for ii = 1..N:
    for jj = j..M:
      d = jj - 7
      c[ii,jj] = c[ii-1, jj+d] + 1
```
The test fires at the top of column 8, before any read of that column would use a stale value (testability), and the escape code finishes the remaining iterations in the original order, so the program neither aborts nor keeps a wrong value; columns 1 through 7 run in the transformed order, where d ≤ 0 holds and the interchange is valid. This is the shape of the paper's dynamic interchange, where the inner loop computes k = 10 - j and the test is k < 0. For tiling the same idea tests the enabling condition before entering the tiled loop, or adjusts the tile size as b = min(k, maxTileSize) when correctness needs k > b.

## Concepts and terms

[1] Transition systems and correct translation.
A transition system S = (V, O, Θ, ρ) is a state machine: V is a set of typed state variables (a state interprets them), O ⊆ V are the observable variables, Θ is the initial condition, and ρ relates a state to its possible successors, referring to unprimed (old) and primed (new) values of the variables; one transition can model a whole basic block or execution path. A computation is a maximal finite or infinite state sequence starting in a Θ-state, with consecutive states related by ρ. The system is deterministic when the observable part of the initial condition determines the rest of the computation, and the paper restricts itself to such systems. Two systems are comparable when their observables correspond one-to-one; a source and a target state are compatible when corresponding observables have equal values. The target is a correct translation (refinement) of the source when for every pair of computations with compatible initial states, the target terminates iff the source does, and their final states are compatible. The contract compares observable behavior, not internal states.

[2] Translation validation and VOC-64.
Translation validation checks a single compiler run: the emitted target code must be proved a correct translation of the input, instead of the compiler being proved correct once for all inputs. VOC-64, the tool used here, reads the compiler's optimization specification, or falls back on heuristics that recover the reindexing function by comparing source and target when no specification is available, generates the verification conditions, and passes them to CVC, an automatic theorem prover for quantifier-free formulas over theories of arrays, linear arithmetic, abstract data types, and uninterpreted functions. CVC can also emit proofs so that results can be confirmed by an independent proof checker, supporting self-certifying compilers that ship a proof with the compiled code. The CVT prototype verified about 10,000 lines of source in ten minutes but was restricted to programs with a single external loop and a limited set of optimizations; simulation-based methods handle nested loops but only structure-preserving optimizations.

[3] Rule VALIDATE.
For structure-preserving optimizations, VALIDATE proves correct translation by abstraction rather than by matching states. A cut-point set CP of a program contains its initial and terminal blocks and at least one block of every cycle, so any path splits into simple path segments between cut-points; ρ_ij is the compressed transition relation of a simple path from block Bi to Bj. The rule supplies a control abstraction κ from target cut-points to source cut-points that preserves initial and terminal status; an invariant ψ_i for each target cut-point (usually obtainable from the compiler's data-flow analysis); and a data abstraction α: (PC = κ(pc)) ∧ ⋀_k (p_k → V_k = e_k), which states that the programs are at corresponding control points and conditionally equates source variables V_k with expressions e_k over target variables, possibly with several clauses for one variable. At initial target blocks one must have Θ_S ∧ Θ_T → α ∧ ψ_i, and at terminal blocks α must imply agreement of the observables. For each simple target path from Bi to Bj the rule forms one verification condition: ψ_i, α, and ρ_ij, together with the source steps available at κ(i), imply that the data abstraction and ψ_j hold afterwards. This version eliminates the existential quantifier over source paths that its predecessor carried, which makes the conditions quantifier-free; the two versions are equivalent under determinism. Validity of all conditions implies that the target is a correct translation of the source.

[4] Reordering transformations and their canonical form.
A reordering transformation changes only the order in which the original statements execute; statements are neither added nor deleted. A dependence runs from one access to a location to another access to the same location where at least one is a write, and a transformation preserves it when it keeps the relative order of the two accesses. The generic loop `for i ∈ I by ≺_I do B(i)` has a finite iteration space I defined by linear inequalities over the loop indices and a total order ≺_I, usually lexicographic; a reordering is written `for j ∈ J by ≺_J do B(F(j))`, where F: J → I is a bijection giving the body executed at each position of the new order, and F⁻¹ gives the new position of each original iteration. Interchange, reversal, and skewing are instances with different F and orders; skewing also changes the body, so it is not a reordering in the strict sense, yet the method still applies. Tiling's F uses existential quantifiers (a point belongs to a tile), and the resulting conditions remain solvable by CVC. Fusion and distribution are handled by a generalization in which the loop body is partitioned into segments that move to different iterations. The tiling examples assume that the tile size divides the loop bounds evenly.

[5] Rule PERMUTE and its soundness.
The rule has two premises: F is a bijection from J onto I, and for all i1, i2 ∈ I with i1 ≺_I i2 and F⁻¹(i2) ≺_J F⁻¹(i1), that is, for the pairs whose order the transformation reverses, B(i1);B(i2) ~ B(i2);B(i1). Here P ~ Q means that P and Q produce the same result when executed from an arbitrary initial state; the relation is reflexive, transitive, and closed under sequential composition. Under these premises the source loop and the transformed loop are equivalent. The soundness proof (Lemma 1) is an induction over the source prefixes: the body of a new iteration is bubbled left into its place, swapping past the transformed iterations that follow it, and every swap is licensed by the second premise. In practice the compiler supplies F with its optimization specification, or heuristics identify F from a comparison of source and target, and the validator still checks that F is a bijection and that the body pairs commute.

[6] The simplified dependence rule.
The classical safety criterion for reordering requires the transformation to preserve the relative order of every pair of accesses to the same location where at least one access is a write: a flow dependence (write followed by read), an anti-dependence (read followed by write), or an output dependence (write followed by write). Let D(i) be the location written in iteration i, U(i) the location read, and P(i) the position of iteration i in the transformed order. The simplified rule requires, for all i < j in the source order, D(i) = U(j) or U(i) = D(j) or D(i) = D(j) implies P(i) < P(j). It is stricter than PERMUTE, which accepts programs such as `a[i,j] = a[i-1,j+1] - a[i-1,j+1]` whose reorderings reverse flow dependences yet compute the same results; CVC checks confirm that for reversal and interchange with simple bodies, satisfying the simplified rule implies satisfying PERMUTE. The run-time technique uses the flow-dependence-only version: for all i < j, D(i) = U(j) implies P(i) < P(j).

[7] Run-time validation of speculative optimizations.
When aliasing (pointers, computed indices) blocks static dependence analysis, correctness is enforced at run time. The safety requirements are: the test determines and reports a possible dependence violation, precisely or conservatively; on failure an execution path still produces the correct result; and the test fires before the violation actually occurs, which is called the testability property. The efficiency targets are that the test occurs as rarely as possible, is cheap in time and space, and that recovery costs no more than the unoptimized loop. A simple test without testability walks the transformed order, records for each location the largest source index of an iteration that has read it (MARK[U(k)] := max(MARK[U(k)], k)), and fails when an iteration k about to write finds a larger index (MARK[D(k)] > k); it detects the problem after the stale read has already been consumed, which makes it useless for validation. If the test must be integrated into the optimized loop and each D(j) computed only in its own iteration, no algorithm can have testability for arbitrary D and P. In the common case where the loop writes a[i] and reads a[U(i)], leaving only U complex (aliased), the test for iteration i with read index r = U(i) is test(i,r) = r < i ∧ P(r) > P(i); for reversal it reduces to r < i, for interchange to r1 < i1 ∧ r2 > i2. Testability holds when only flow dependences are at issue; anti-dependences can be ignored under constraints such as U(i) < i. The compiler specializes the test to the transformation and hoists it when it is invariant in an inner loop (the paper's dynamic interchange computes k = 10 - j once per outer iteration and tests k < 0); on failure the code escapes to a copy of the original loop that executes the remaining iterations in the original order. Tiling instead tests the enabling condition before entering the tiled loop or picks b = min(k, maxTileSize) when correctness needs k > b. On ILP processors the test can fill otherwise idle issue slots, and IA-64 offers dynamic disambiguation instructions for aliasing plus predication to disable speculative operations (the software-bubble technique).

[8] Evaluation.
The compile-time experiments validate the successive stages of optimization the SGI Pro-64 compiler applies to an example WHIRL program: the input program, after loop inversion, after constant folding, after copy propagation with dead code elimination, and after strength reduction (five stages). VOC-64 modeled each stage as a transition system and generated the conditions, and CVC checked all of them, showing a condition and its proof for the strength-reduction step. The run-time work covers the tests and escape paths for loop interchange and loop tiling, derived from the general test forms for the specific permutations.
